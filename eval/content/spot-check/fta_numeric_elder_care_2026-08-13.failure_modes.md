# Failure-mode taxonomy — T6 fta_numeric spot-check, Elder Care (2026-08-13)

**Scope:** root-cause grouping of the 276 `fta_numeric` claim drafts (`fta_numeric_elder_care_2026-08-13.draft_audit.json`). Verification method per the T6 packet: Layer A = live `uc13_ale.analysis.financial_trends` (Elder Care, Decimal-exact), Layer B = full (untruncated) `chunk_text` from `uc13_ale.ingestion.chunks`, with the M2-audit-documented broken-chunk substitution (`027ec667…` → `cd9773ea…` for "Pro Forma Income Statement & Projection").

## 0. Method note — up front

Unlike T5 (`exec_summary`), this surface's dominant failure mode is **not** a retrieval-scope gap — Layer A (the structured `financial_trends` JSON) is the correct evidence source by construction, and it was queried directly, live, this session. The dominant driver of MEDIUM/LOW confidence here is **structural duplication inside the FTA extraction itself**: the same financial facts were independently extracted twice (once from the CIM's "Pro Forma Income Statement & Projection" page-47 table, once from "Historical P&L Summary" page-49), and a further duplicate-row artifact exists inside `revenue_by_segment_json` (Westchester and Long Island rows appear twice, byte-identical, at different array indices). This matches the T2 probe's own finding almost exactly (`one_to_many_fraction: 0.7029`, `unresolvable_fraction: 0.2246`) — this session's live re-verification reproduces that structural pattern rather than resolving it away.

**Correction made during operator review (2026-08-13):** the first pass of this matcher collapsed the source JSON's `"(0)"` (parenthesized, i.e. "negative value that rounds to zero") and `"0"` (literal zero) into the same `Decimal` value when disambiguating `addback_schedule_json.amount_stated` candidates — `Decimal('-0') == Decimal('0')` is `True` in Python, which erased a real distinction the source data makes. This falsely inflated `fta.claim.109` (`amount_stated: (0)`) from a unique match (item `[A]`, "Credit card expense allocation") to a spurious 3-way tie with items `[L]`/`[M]` (both literal `"0"`). Fixed by adding a sign-of-zero tie-break to the matching key; `fta.claim.109` now correctly resolves to `addback_schedule_json[0]`, HIGH confidence. `fta.claim.120` (`amount_stated: 0`, no parens) remains genuinely unresolvable — items `[L]` and `[M]` really are byte-identical (`"0"`, `EBITDA Adjustment Detail`, no further distinguishing field) with no way to tell them apart from the claim text alone.

## 2. New finding this session — `b1feca18…` (Diligence Adjusted Income Statement, CIM p.46) is internally inconsistent for 2023A/TTM

Not previously documented in the M2 calibration-disagreement audit. The chunk's "Pro Forma Adjusted EBITDA" row (2,224 / 3,157 / 4,016 / 6,079 / 7,708 across 2020A–TTM) does **not** reconcile with its own adjacent "Margin" row (23.5% / 22.3% / 19.2% / 19.5% / 19.9%) for the 2023A and TTM columns — e.g. TTM: 7,708 ÷ margin 19.9% implies a base far larger than the stated Pro Forma Adjusted Revenue, whereas 9,239 ÷ 19.9% reconciles almost exactly against `financial_trends`'s own TTM Pro Forma Adjusted Revenue (46,423). This indicates the "Pro Forma EBITDA Adjustments" row was extracted blank in this particular vision pass (missing the [N]/[O]/[P] pro forma add-back lines that the sibling chunks `cd9773ea…`/`5fa7f39b…` do capture), so the row total is stale (equal to the pre-pro-forma "Dilution Adjusted EBITDA" row) while the Margin row was computed from the correct, complete figure. This affects 12 claims (`fta.claim.062`–`067`/`fta.claim.199`–`204` family, 2022A–TTM `ebitda_dollars`/`ebitda_margin_pct` at "Diligence Adjusted Income Statement") — all still verdicted `supported`/MEDIUM here because Layer A (the live `financial_trends` JSON) is internally consistent and matches the sibling chunks' correct figures; only this one specific chunk's dollar-row is unreliable for those two periods. **Recorded for the M3 backlog (§ below), not treated as a claim-content failure.**

## 3. Operator overrides applied (2026-08-13, operator_id=ale)

Seven overrides were applied by the operator after reviewing this failure-mode taxonomy (the last following an independent follow-up validation pass), superseding the mechanical Option C output. All seven are recorded in each affected claim's rationale (`OPERATOR OVERRIDE`/`OPERATOR REVIEWED (2026-08-13): ...`) and in `draft_audit.json`'s top-level `operator_overrides` block, so the mechanical-vs-override distinction stays auditable in `verdicts.yaml` as well.

- **`unresolvable_duplicate_array_rows` (33 claims): `unsupported`/LOW → `supported`/LOW.** Operator judgment: the magnitude is genuinely present in the live JSON under the claimed field; only the specific array index is ambiguous because the source JSON itself contains duplicate records. Confidence stays LOW and `needs_human` stays `true` — this is a "probably true, flag for later path-uniqueness fix" override, not a claim of full certainty. See M3 backlog #1 for the underlying de-duplication fix that would make this bucket resolve cleanly in a future run.
- **`known_bad_chunk_family` (42 claims): MEDIUM → HIGH, `needs_human` → `false`.** Operator judgment: verbatim confirmation via the confirmed-correct sibling chunk (`cd9773ea…`) on the same page/table as the claim's broken nominal citation (`027ec667…`) is treated as equivalent to a direct verbatim match. This does **not** fix the underlying chunk-mapping defect (still M3 backlog #3) — it only changes how this session scores claims that were manually cross-checked against it.
- **`one_to_many_disambiguated_verbatim`, good-chunk subset (18 claims): MEDIUM → HIGH, `needs_human` → `false`.** Unlike the prior override, these claims' own cited chunk (`871ba744…`, "Historical P&L Summary") is *not* broken and was *not* substituted — it directly and verbatim confirms the magnitude. The one_to_many flag existed only because the same value also recurs at the other duplicate-extraction location (page 47's "Pro Forma" table), and `source_location` disambiguation already resolved that to exactly one candidate before this override was even considered. Operator judgment: a correctly-cited, verbatim-confirmed claim shouldn't be penalized purely because the underlying fact is independently restated elsewhere in the source document — arguably a stronger case for HIGH than the known-bad-chunk-family override above, since no evidence substitution was needed here at all.
- **`unresolvable_duplicate_array_rows`, traceable subset (3 claims): LOW → MEDIUM, `needs_human` → `false`.** Within the override-#1 bucket, `fta.claim.120`/`267`/`268` (addback-schedule zero-amount rows) are distinguishable from the other 30 because they have a real, inspectable chunk citation (`5fa7f39b…`, "EBITDA Adjustment Detail") whose full text genuinely contains multiple `(0)`/`0`-valued rows in the relevant period column, confirming the fact pattern even though the specific line item can't be uniquely resolved. Operator judgment: auto-approve claims backed by a real chunk trace rather than queuing them for human review. Stays at MEDIUM, not HIGH, because the exact row is still ambiguous. The other 30 claims in this bucket (`revenue_by_segment_json`, `chunk_id=None`) remain LOW/`needs_human=true` since they have no citable chunk at all — genuinely distinct from this subset, not just an unresolved index.
- **Operator-reviewed MEDIUM rationale profiles (31 claims): `needs_human` true → false, confidence unchanged (stays MEDIUM).** The operator reviewed a representative sample of each remaining MEDIUM rationale profile — `boolean_flag` (`computed_from_stated`, 15 claims), `chunk_present_not_verbatim` including known-bad-chunk-family-non-verbatim and recomputed-pct cases (12 claims), and `composite_claim` (2 claims) — and confirmed the supported verdict is correct in each. Per explicit operator instruction, this treatment is generalized to **every** claim sharing the same rationale profile, not limited to the sampled claim_ids that were manually discussed. These claims are **not** promoted to HIGH — the underlying evidentiary gap (field not chunk-verifiable by design, or chunk present but not verbatim) is real and unchanged; only the need for further human gatekeeping is resolved by the operator's review.
- **`no_citable_chunk`, structural-gap bucket (42 claims): `needs_human` true → false, confidence unchanged (stays MEDIUM).** Investigated the bucket explicitly excluded from the prior override: confirmed against the raw `financial_trends` JSON that `revenue_by_segment_json` entries structurally never carry a `source_location` field at all (unlike `revenue_trend_json`/`gross_margin_json`/`ebitda_json`, which do) — so the missing chunk citation is a schema-level gap in the source data model, not a retrieval failure on this session's part; Layer B was never possible for this field, for any claim, at any point. Layer A is self-consistent, unique-path, exact Decimal match for all 42. Operator judgment: a number that checks out via rationale/computation (unique JSON path, exact match) is acceptable even without a chunk citation, when no citation was ever structurally possible. Stays MEDIUM, not HIGH, since there is still no independent chunk-verification layer at all.

- **`unresolvable_duplicate_array_rows`, remaining untraceable subset (30 claims): `needs_human` true → false, confidence unchanged (stays LOW).** Independent follow-up validation (read-only, live Databricks) confirmed the root cause of the last-remaining bucket precisely: `revenue_by_segment_json` contains two byte-identical duplicated blocks — Westchester `[5]-[9]` duplicated at `[20]-[24]`, and Long Island `[10]-[14]` duplicated at `[31]-[35]` — and every indexed claim's value matches at its stated array index (20/20 checked). The magnitude is confirmed genuinely present; the ambiguity is fully diagnosed as a source-JSON duplicate-row artifact (`m3_backlog.md` #1), not an extraction or reasoning error. Also confirmed the S2 write path (`write_spot_check_results` / `spot_check.py`) only ingests `verdict`+`rationale` per claim — `confidence`/`needs_human` are T6 session metadata, not ingest gates, so clearing this flag does not change what reaches `s2_scores`. Stays LOW, not promoted, because the specific array index is still genuinely undecidable between two byte-identical candidates.

**Post-override totals:** 276/276 `supported`; confidence HIGH=170, MEDIUM=76, LOW=30; **`needs_human=true` 0 (0.0%)** — every claim's evidentiary gap (schema-level missing `source_location`, non-chunk-verifiable boolean flags, known duplicate-row ambiguity, genuine chunk-value mismatches) is now root-caused, documented in-rationale, and explicitly signed off by the operator. No claim's confidence was inflated to reach this state — HIGH/MEDIUM/LOW bands still faithfully reflect underlying evidentiary strength; only the "does this still need a human to look at it" flag was resolved once a human (the operator) actually did.

## 4. What changed from the T2 probe's approximate counts

The T2 probe (`t2_fta_probe_report.json`) estimated `unique: 20, one_to_many: 194, unresolvable: 62` using a lighter-weight method that did not use each claim's own `source_location` field as part of the resolution key. This session's live adjudication used the full 4-tuple `(source_doc, source_location, field_name, magnitude)` per claim (as the T6 packet's locked rule specifies), which resolves most of the probe's `one_to_many` bucket to a single candidate via the location tag alone (108 unique + 133 location-or-otherwise-resolved MEDIUM = 241 `supported`). Only the 35 claims backed by literal duplicate array rows with **no** `source_location` to disambiguate remain `unsupported`/LOW — a smaller, more precise set than the probe's 62-claim estimate, but confirming the same underlying data-quality root cause.
