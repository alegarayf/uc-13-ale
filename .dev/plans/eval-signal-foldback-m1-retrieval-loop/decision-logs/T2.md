# T2 — Preflight epoch-pin + gold-drift check

**Plan:** eval-signal-foldback-m1-retrieval-loop · **Subtask:** T2 · **Date:** 2026-08-20

## Chosen approach

Added `eval/retrieval/scripts/preflight_epoch_pins.py` with `check_epoch_pins(store, ...)` that:

1. Loads each D4-pinned baseline manifest via `EvalStore.get_run(run_id)` (not raw SQL in the comparison path).
2. Computes current pins with the same helpers and filters as `EvalHarness.run`: `compute_gold_snapshot` over gold labels filtered by `company_name` + `catalog`, and `compute_registry_hash` over the shared `intent_registry.yaml`.
3. Compares stored manifest pins to current values with **exact string equality** (no fuzzy/normalized comparison).
4. Reports drift as structured data (`EpochPinCheck`) and stdout lines; does not raise for pin mismatch (preflight informs, it does not abort the tool).
5. Exposes a live path via `WarehouseEvalStore` + Databricks SQL warehouse (`databricks_sql_executor`), read-only, for T3 operator preflight.

**Flag 4 (sibling baseline JSONs not committed):** Verify the three non-Elder sibling baselines against `uc13_ale.ops.retrieval_harness_runs` by explicit `run_id` through `get_run`, rather than committing missing local `reports/*.json` artifacts. Elder Care already has `baseline_2fa3a9056bd0.json` committed; siblings exist in ops only per plan assumption §5.2 item 5.

**Flag 8 (dirty gold vs pinned gold_snapshot):** Use exact-match comparison of full SHA-256 hex digests for both `gold_snapshot` and `registry_hash`, mirroring `EvalHarness.validate_baseline_ref` (which also exact-compares `ingestion_snapshot`, but T2 scope is gold + registry only per packet). Any mismatch surfaces `gold_snapshot_match=False` / `registry_hash_match=False` before T3 submit.

## Alternatives rejected

- **Commit sibling baseline report JSONs locally (Flag 4):** Rejected — plan non-goal explicitly forbids committing the three missing sibling JSONs; ops is the source of truth for those run_ids.
- **Fuzzy / normalized gold comparison (Flag 8):** Rejected — would diverge from `validate_baseline_ref` and could admit drift that T3's live preflight would still reject, creating silent T2/T3 disagreement (plan §5.4 coupling surface 2).
- **Raw SQL column reads without `EvalStore`:** Rejected for the comparison core — kept `get_run` as the manifest access path; warehouse SQL is isolated to `WarehouseEvalStore` for laptop execution only.

## Assumptions made

- `uc13_ale.ops.retrieval_harness_runs` carries `gold_snapshot` and `registry_hash` columns per `apply_ops_ddl.sql` (verified before implementation).
- The four D4 `run_id`s exist in ops with `harness_status=complete` and `run_type=baseline` at T3 execution time (plan §5.2 item 5).
- Committed `gold_labels/*.yaml` and `intent_registry.yaml` at T3 time will match the pins baked into each baseline manifest, or T3 skips that company (assumption §5.2 item 6).
- `check_epoch_pins` gold filtering (`company_name` + `catalog`) matches `EvalHarness.run` — T3 must use the same gold files when building manifests.

## Items deferred

- **Ingestion snapshot pin check:** Out of T2 scope; T3's live `validate_baseline_ref` still checks `ingestion_snapshot`. If T2 pass and T3 fail on ingestion only, that is expected asymmetry — note in T3 decision log.
- **Hermetic test for `WarehouseEvalStore` SQL row parsing with live array shapes:** Live warehouse is the falsifier; unit tests use `SqliteEvalStore` / mock `get_run` only (per packet Tests contract).
- **Adversarial gap — multi-company gold file with wrong `company_name` on rows:** Covered indirectly via `PreconditionError` when no labels match filter; no separate cross-company contamination test added (single-company pin tests suffice for M1).
